# Развёртывание v2 в Coolify

## Подготовка и резервная копия

1. Проверьте права аккаунта Finam на Si, стакан, поток публичных сделок, OI, хранение и использование данных через MCP. Trade API публикует 200 REST-запросов в минуту на метод. Доступную глубину и лимит подписок проверьте для своего доступа. Сначала оставьте текущий `POLL_SECONDS`.
2. Отключите автодеплой экспериментальной ветки. Сохраните SHA работающих образов Collector и MCP, настройки и сетевую конфигурацию Coolify. Используйте отдельные staging экземпляры и базу. Для REST и MCP сохраните существующие секреты в хранилище Coolify.
3. Сделайте дамп базы коллектора. Внутри доверенной среды, где роль и пароль передаются через настройку libpq, проверьте копию в отдельной базе. База PostgreSQL должна оставаться во внутренней сети. Резервируйте OAuth-базу Keycloak отдельно по действующей инструкции.

   ```sh
   pg_dump --format=custom --file=finam-pre-v2.dump finam
   pg_restore --list finam-pre-v2.dump
   pg_restore --exit-on-error --no-owner --dbname=finam_restore_check finam-pre-v2.dump
   ```

   Сверьте количество строк и даты свечей по символу/интервалу, а также `backfill_status` в базе проверки. Скрипт v2 аддитивный, выполняется в транзакции с advisory lock и сохраняет старые таблицы. Для отката приложения достаточно вернуться к старому Collector и MCP. Ручной restore предназначен для отдельной базы и применяется к production только после согласования.

## Конфигурация

| Переменная Collector | Назначение |
| --- | --- |
| `MARKET_V2_MODE` | `off` по умолчанию. На staging используйте `rest` для проверки формата и прав перед `stream` |
| `MARKET_V2_SYMBOL` | Необязательный явный символ для сбора. По умолчанию Finam Assets/GetAsset выбирает ближайшую подтверждённую экспирацию Si |
| `MARKET_V2_BOOK_SECONDS` | Сохранение изменённого стакана в потоке или polling в REST, по умолчанию 5 с |
| `MARKET_V2_TRADES_SECONDS` | REST polling последних сделок, по умолчанию 30 с, минимум 15 с |
| `MARKET_V2_QUOTE_SECONDS` | REST polling котировки и OI, по умолчанию и минимум 15 с. Частоту биржевой публикации этот параметр не задаёт |
| `MARKET_V2_NEXT_CONTRACT_CANDLES` | `true` включает минутные свечи следующего контракта. По умолчанию `false` |
| `MARKET_V2_SESSIONS_FILE` | Путь до доступного для чтения файла расписания из подтверждённого биржевого календаря, сгруппированного по MIC и московской календарной дате |
| `MARKET_V2_DISK_PATH` | Файловая система контейнера, видимая для мониторинга. Фактический диск PostgreSQL измеряйте на сервере БД |
| `MARKET_V2_READ_DATABASE_URL` | Необязательный DSN выделенной роли с SELECT на таблицы v2 и свечи. При отсутствии читается через обычный DSN в read-only транзакции |
| `RESEARCH_API_TOKEN` | Существующий общий секрет из Coolify длиной от 32 символов. Указать в обоих приложениях, доступ к REST v2 только из приватной сети |
| `FINAM_MAX_REQUESTS_PER_SECOND` | Общий throttle HTTP-клиента Finam, по умолчанию 3. Изменять после наблюдения за 429 и задержками |

Формат расписания — `{"RTSX":{"YYYY-MM-DD":[["start-ISO-with-offset","end-ISO-with-offset"]]}}`. Праздничный день задаётся явно пустым массивом. Для клиринга или перерыва передайте два интервала. Даты составляются из [официального календаря MOEX](https://www.moex.com/ru/tradingcalendar?market=derivatives-market) или лицензированного [машиночитаемого календаря](https://www.moex.com/a2836). Отсутствующая дата даёт `UNKNOWN`. Автоматический импорт расписания ещё не реализован.

Разверните Collector из корня репозитория с `Dockerfile`, затем MCP из существующего Compose. Для API и MCP используется существующая авторизация. Сохраните сетевые правила из [текущей инструкции MCP](CHATGPT_MCP_SETUP.md). Маршрут `/api/v2/*` остаётся на приватном Collector и через Caddy не проксируется.

## Staging и переключение

1. Загрузите восстановленную базу в staging. Запустите Collector с `MARKET_V2_MODE=off` и проверьте `/health`, `/bars`, старый MCP и сохранность таблиц. Прогон на локальном PostgreSQL 16 подтвердил повторное применение SQL и восстановление 320 свечей из дампа. Доступ к production-БД для такой проверки не использовался.
2. Включите `rest` на одну сессию. Сверьте точные символы, реальные размеры и времена сделок, текущее состояние стакана и наличие OI. Отдельно проверьте `/api/v2/health/data-quality` и `/api/v2/market/capabilities`.
3. Перейдите на `stream`. Сверяйте текущий стакан с REST, отдельно проверьте переподключение и наличие документированного snapshot flag в реальном WS. При отсутствии флага будет сохраняться REST-снимок. Потери в ленте после разрыва остаются неизвестными.
4. Убедитесь, что нагрузка, скорость роста диска и частота 429 укладываются в бюджет. Проверьте интервалы публикации OI, закрытый рынок и переключение контракта. Для проверки дат и перерывов примените актуальный файл расписания.
5. После согласования production-переключения разверните те же SHA, проверьте legacy и v2, затем обновите MCP в ChatGPT. Для отката остановите v2 через `MARKET_V2_MODE=off` либо верните прежние образы. Снимки, сделки и свечи останутся в базе.

## Бюджет диска и retention

Расчёт на один инструмент, 25 торговых дней за 30 календарных, до 18 часов/день и примерно 180 байт на строку уровня с индексами. При снимке каждые 5 с получаем до 324 000 снимков/30 дней. При 20–100 записанных уровнях это около **1,2–5,8 ГБ за 30 дней** плюс заголовки, WAL и запас. При 10–100 сделках/с и 330 байтах на сделку с индексами ориентир **5,4–53,5 ГБ за 30 дней**. Размер строки оценён по локальному прогону с агрегатами, реальные ID и структура индекса могут дать другой результат. WAL, бэкап и раздувание требуют отдельного свободного места. На staging проверьте реальный пиковый trades/s и рост `pg_total_relation_size` за полную сессию.

Предварительные сроки после измерений — стакан 7–30 дней, сделки 30–90 дней, агрегаты 15 с 180 дней, минутные агрегаты, свечи и OI долгосрочно. Выборку текущих объёмов можно выполнить ролью мониторинга:

```sql
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_statio_user_tables
WHERE relname IN ('orderbook_snapshots','orderbook_levels','market_trades',
                  'market_flow_aggregates','market_quotes','open_interest_history','candles')
ORDER BY pg_total_relation_size(relid) DESC;
```

Автоматическая очистка и партиционирование в этой ветке отсутствуют. Объёмы измеряются через PostgreSQL и системные счётчики. Настройте оповещения о свободном диске на сервере БД до включения длительного сбора. Для больших объёмов проверьте архивирование с сохранением минутных агрегатов и план партиционирования до утверждения сроков.
